# 運休予測の精度測定（2026年11月16日）

作り直しの前に、現在の2つの予測の仕組みを同じ物差しで採点しました。結論は「どちらも当てずっぽうより少し良い程度で、冬の最大級の大雪を前日に見抜けていない」です。ただし冬の運休の実例は17路線日（独立した嵐は約7回）しかなく、数値の幅は大きいです。

## 測り方

| 項目 | 内容 |
| --- | --- |
| 単位 | 路線 × 日（JST）。「その日、その路線で天気が原因の運休があったか」 |
| 正解（運休あり） | 収集したJR公式文（2026-02-20〜11-16、11.1万行）で、路線名と日付が明記された気象原因の運休 33路線日。加えて過去資料の大雪（2022-02-06/21、2025-12-14、2026-01-25）10路線日 |
| 正解（平常） | 観測が1日6回以上あり、運休も原因不明の運休も無かった 1,919路線日 |
| 除外 | 熊・踏切・急病・地震・計画除雪など気象以外（58）、原因不明・路線名なし（13） |
| 入力 | **前日に発表されていた予報**（Open-Meteo 予報アーカイブ）。積雪深は前日21時の値。2022年分のみ当日予報。JR公式情報・投稿・実測は入れない |
| 採点対象 | A: `lib/prediction-engine`（`/api/prediction/v2`、今の主画面）／B: `lib/forecast/risk`（旅程API）／比較用の単純な目安（最大瞬間風速、1時間最大降雪量、1時間最大降水量） |

AUCは「運休日を平常日より高く順位付けできるか」（0.5=当てずっぽう、1.0=完全）。

## 結果

### 冬（11〜3月）: 運休17 / 平常708

| 方式 | AUC | 警告の基準 | 運休を検出 | 平常日に警告 |
| --- | --- | --- | --- | --- |
| A（今の主画面） | 0.61 | 25%以上（「遅延」表示） | 11/17 | **65%（457日）** |
| A | | 65%以上（「見合わせ」表示） | 5/17 | 6% |
| A（積雪深の単位を修正） | 0.66 | 65%以上 | 7/17 | 6% |
| B（旅程API） | 0.75 | high以上 | 5/17 | 4% |
| 1時間最大降雪量のみ | 0.95 | 1cm/h以上 | 8/17 | 3% |
| 最大瞬間風速のみ | 0.72 | 20m/s以上 | 4/17 | 9% |

### 冬以外: 運休26 / 平常1,211

| 方式 | AUC |
| --- | --- |
| A | 0.56 |
| B | 0.54 |
| 1時間最大降水量のみ | 0.84 |

## 分かったこと

1. **A（今の主画面）は冬の平常日の65%で「遅延」以上を表示しています。** 冬の平常日の中央値が27%で、冬季の底上げ（`MIN_WINTER_RISK` 等）により、ほぼ毎日警告が出る状態です。
2. **冬以外はA・Bともほぼ当てずっぽう（AUC 0.54〜0.56）。** 夏の運休は大雨が原因ですが、どちらも雨をほとんど評価できていません。単純な「1時間最大降水量」のほうが良い順位付けをします。
3. **最大級の大雪を前日に見抜けていません。** 2022-02-06と2026-01-25の札幌圏の大規模運休では、前日の予報自体が1時間0.6〜1.7cmの降雪しか示しておらず、A・Bとも低い値でした。ルールの調整だけでは解決せず、入力（局地的な大雪に強い気象庁の予報・警報、24〜48時間の累積）を変える必要があります。
4. **Aのバグ:** 積雪深をcmとして判定していますが、天気取得はメートルで渡しています。「地吹雪」「累積積雪」のルールは本番で一度も働きません。単位を直すとAUCは0.61→0.66。
5. 「1時間最大降雪量のみ」の0.95は**楽観的すぎる値**です。平常日に12〜2月が含まれず（収集開始が2月20日）、「雪は降るが運行できた日」がほぼ無いためです。この冬のデータで再評価が必要です。

## 限界

- 冬の運休17路線日は約7回の嵐に集中しており、独立した事例は少数です。検出率の95%区間は±20ポイント以上あります。
- 8月27〜28日の大雨は公式文に多数の路線が列挙されており、一部は過剰なラベルの可能性があります。
- 「一部列車の運休」も「全面運休」も同じ「運休あり」として扱っています。

## 次の一手

- 予測の中核を1本に作り直す。入力は24〜48時間の累積降雪・最大瞬間風速・降水量と路線ごとの弱さ。今回の物差しでA・Bと単純な目安の両方に勝つことを条件にする。
- 気象庁のメソ予報（MSM）と警報・注意報の予測を入力に加え、全球モデルが過小評価する局地的な大雪に対応する。
- この冬（12〜2月）の15分収集データで平常日を補い、毎月再評価する。収集の修正デプロイが前提。

## 追記：中核の作り直し（risk-core-1.0）

旅程API（主画面）の気象判定 `lib/forecast/risk.ts` の中身を、新しい中核 `lib/forecast/core.ts` に置き換えました。画面に返す形（レベル・根拠・地点数）は変えていません。

### 中身

- 入力: 各地点・各時刻の「1時間降水量」「1時間降雪量」「直前24時間の降雪合計」「直前24時間の雨量」。重みはすべて0以上（雪や雨が増えてリスクが下がることはない）。
- 当てはめ: 本番と同じ「1日のうち最も悪い時刻・地点」で学習するロジスティック回帰。係数は `lib/forecast/core-coefficients.json`（`scripts/eval/fit-core.ts` が生成。手で編集しない）。
- レベル: 運休の無かった日の誤警報率が 15% / 4% / 1% になる値で「変化に注意」「移動計画の見直しを」「強い気象リスク」を分けた。
- 風: 当てはめでは重み0（強風の運休は2〜3件しかなく、予報の突風は運休を見分けられなかった）。強風規制は実在するため、突風25m/s以上の予報は当てはめとは別に一律「変化に注意」以上にする。
- 欠損: 地点の欠け、冬の24時間分の欠けは従来どおり「不明」。当日の気象庁警報・降雪観測の上乗せも従来どおり。

### 交差検証（週ごと10分割。同じ嵐は学習と評価に分かれない）

| | AUC 全期間 | 冬 | 冬以外 | 誤警報 15% / 4% / 1% で検出（43件中） |
| --- | --- | --- | --- | --- |
| 新しい中核 | **0.80** | **0.93** | **0.71** | **26 / 15 / 11** |
| 旧B（以前の主画面） | 0.62 | 0.75 | 0.54 | 15 / 6 / 2 |
| 旧A（v2 API） | 0.55 | 0.61 | 0.56 | 11 / 6 / 3 |
| 降水量だけの同じ当てはめ | 0.79 | 0.86 | 0.76 | 18 / 9 / 4 |

注意: 交差検証では折りごとに尺度が変わるため、当てはめ無しの単一指標（「1時間最大降水量」AUC 0.84）とは直接比べられません。同じ手順で当てはめた「降水量だけ」との比較で、検出数は大きく改善しています。特徴の組み合わせもこの結果を見て選んだため、値はわずかに楽観的です。

### 真冬の確認（ラベル無し）

2025-12-11〜2026-02-19 の全路線日に当てはめると、「移動計画の見直しを」以上は 11.6%、「変化に注意」以上は 28%。旧Aの「冬の平常日の65%で遅延表示」より大幅に抑制的ですが、正解ラベルが無いため妥当かは未確認です。この冬の15分収集のデータで確認し、再当てはめします（`scripts/eval/deep-winter-check.ts`）。

### 同時に直した不具合

- 気象予報・気象庁警報・アメダスの取得が Next.js のキャッシュ（stale-while-revalidate）を通っており、開発環境で1か月前（10月12〜19日）の予報が返っていた。古い予報が今日を含む場合、取得時刻を「今」と表示したまま古い予報で判定してしまう。3つとも `cache: 'no-store'` にし、各モジュール自身の5〜15分キャッシュだけを使うようにした。
- 旧Aの積雪深の単位不一致は、旧Aを使う v2 API の整理（作り直しの次の段階）で扱う。主画面は旧Aを使っていない。
